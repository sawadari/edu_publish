# 第4回: ヘタな要求あるある ── 8つの改善パターンで曖昧性を排除する

## この記事を読んでほしい人

- 「使いやすいこと」「高速であること」と書いて、レビューでダメ出しされた人
- 要求を書いたけど、開発者から「これ、どういう意味？」と聞かれた人
- 「良い要求」の基準が分からない人

## はじめに: 「使いやすくしてください」は要求ではない

前回、ニーズを要求に変換する方法を学びました。

でも、実際に要求を書いてみると、こんな問題に直面します:

**書いた要求**:
```
REQ-001: AGVは使いやすくなければならない
REQ-002: AGVは高速に動作しなければならない
REQ-003: AGVは安全でなければならない
```

**レビューでのダメ出し**:
```
レビュアー: 「これ、曖昧すぎて実装できないよ」
あなた: 「え、でもshall使ってますよ？」
レビュアー: 「shallだけじゃダメなんだよ…」
```

この記事では、**誰が読んでも同じ意味に解釈できる「良い要求」**の書き方を、8つの原則で解説します。

---

## 1. 良い要求の3つの条件

まず、「良い要求」とは何かを定義します。

### 条件1: 明確性（Clarity） - 誰が読んでも同じ意味

**悪い例**:
```
❌ REQ-001: AGVは高速に動作しなければならない
```

**問題**: 「高速」って何？
- Aさんの解釈: 時速5km
- Bさんの解釈: 時速10km
- Cさんの解釈: 応答時間0.1秒

**良い例**:
```
✅ REQ-001: AGVは最高時速3kmで移動しなければならない
```

**ポイント**: 数値で書けば、誰が読んでも同じ意味

### 条件2: 検証可能性（Verifiability） - テストで確認できる

**悪い例**:
```
❌ REQ-002: AGVは十分に安全でなければならない
```

**問題**: 「十分に」をどうやって確認する？

**良い例**:
```
✅ REQ-002: AGVは前方15m以内の障害物を検知率99%以上で検知しなければならない
```

**テスト方法**: 15m先に障害物を100回置いて、99回以上検知できればOK

### 条件3: 実現可能性（Feasibility） - 技術的に可能

**悪い例**:
```
❌ REQ-003: AGVは100kgの荷物を時速50kmで運搬しなければならない
```

**問題**: 物理的に無理（バッテリーと安全性の制約）

**良い例**:
```
✅ REQ-003: AGVは50kgの荷物を時速3kmで運搬しなければならない
```

**確認方法**: 設計段階で実現可能性を検証

## 2. 曖昧な言葉を排除する - 8つの原則

### 原則1: 抽象的な形容詞を使わない

**ダメな言葉リスト**:

| ダメな言葉 | 問題点 | 良い書き方 |
|----------|--------|----------|
| 使いやすい | 何を持って「使いやすい」？ | ボタン3クリック以内で操作完了 |
| 高速 | 何秒？ | 応答時間100ms以内 |
| 安全 | 何をもって「安全」？ | 障害物検知率99%以上 |
| 大量 | 何件？ | 同時100ユーザーまで対応 |
| 簡単 | 何をもって「簡単」？ | マニュアル不要で操作可能 |
| 十分 | どれくらい？ | 具体的な数値を書く |

**書き換え例**:

| 悪い要求 | 良い要求 |
|---------|---------|
| ❌ AGVは使いやすくなければならない | ✅ AGVの操作は、タッチパネルで3ステップ以内に完了しなければならない |
| ❌ AGVは高速に動作しなければならない | ✅ AGVは移動指示受信後、5秒以内に移動を開始しなければならない |
| ❌ AGVは大量のデータを保存できなければならない | ✅ AGVは運搬履歴を1000件まで保存できなければならない |

### 原則2: 「適切に」「十分に」「必要に応じて」を使わない

これらは**逃げ言葉**です。

**悪い例**:
```
❌ REQ-001: AGVは適切な速度で移動しなければならない
❌ REQ-002: AGVは必要に応じてバッテリーを充電しなければならない
❌ REQ-003: AGVは十分な性能を持たなければならない
```

**良い例**:
```
✅ REQ-001: AGVは時速3kmで移動しなければならない
✅ REQ-002: AGVはバッテリー残量20%以下で充電ステーションに移動しなければならない
✅ REQ-003: AGVは50kgの荷物を30m運搬できなければならない
```

### 原則3: 「など」「等」を使わない

**悪い例**:
```
❌ REQ-001: AGVは障害物（人、フォークリフト等）を検知しなければならない
```

**問題**: 「等」に何が含まれる？
- 段ボール？
- パレット？
- 小さなネジ？

**良い例**:
```
✅ REQ-001: AGVは以下の障害物を検知しなければならない:
  - 人（高さ50cm以上）
  - フォークリフト
  - パレット（高さ15cm以上）
```

**ポイント**: 全て列挙する。列挙できないなら、条件で定義する（例: 高さ○cm以上）

### 原則4: 主語を明確にする

**悪い例**:
```
❌ REQ-001: 荷物は50kg以下でなければならない
```

**問題**: 誰が／何が「50kg以下」にするの？
- AGVが50kg以下の荷物を運ぶ？
- 作業員が50kg以下の荷物を載せる？
- システムが50kg以上を拒否する？

**良い例**:
```
✅ REQ-001: AGVは50kgまでの荷物を運搬しなければならない
✅ REQ-002: AGVは50kgを超える荷物が載せられた場合、警告を表示しなければならない
```

### 原則5: 否定形ではなく肯定形で書く

**悪い例**:
```
❌ REQ-001: AGVは障害物に衝突してはならない
```

**問題**: 「衝突しない」だけでは、何をすべきか不明

**良い例**:
```
✅ REQ-001: AGVは前方15m以内の障害物を検知しなければならない
✅ REQ-002: AGVは障害物を検知した場合、1m手前で停止しなければならない
```

**ポイント**: 「〜してはならない」ではなく、「〜しなければならない」

### 原則6: 複数の条件を1つの要求に詰め込まない

**悪い例**:
```
❌ REQ-001: AGVは50kgの荷物を運搬し、障害物を回避し、
            バッテリー残量を監視し、8時間稼働しなければならない
```

**問題**:
- 4つの条件が混じっている
- 1つでも満たせなかったら全体NG？

**良い例（分割する）**:
```
✅ REQ-001: AGVは50kgまでの荷物を運搬しなければならない
✅ REQ-002: AGVは障害物を検知して回避しなければならない
✅ REQ-003: AGVはバッテリー残量を監視し、20%以下で警告を出さなければならない
✅ REQ-004: AGVは8時間連続稼働できなければならない
```

**ルール**: 1要求1条件

### 原則7: 「または」は使わない

**悪い例**:
```
❌ REQ-001: AGVは赤外線センサーまたはLiDARで障害物を検知しなければならない
```

**問題**: どっち？ 両方？ どちらか一方？

**良い例（分割する）**:
```
✅ REQ-001: AGVは前方15m以内の障害物を検知しなければならない
（注: 実装方法は設計段階で決定）
```

または

```
✅ REQ-001: AGVは赤外線センサーで障害物を検知しなければならない
✅ REQ-002: AGVはLiDARで障害物を検知しなければならない
```

### 原則8: 単位を必ず書く

**悪い例**:
```
❌ REQ-001: AGVは50まで の荷物を運搬しなければならない
❌ REQ-002: AGVは8時間稼働しなければならない
```

**問題（1つ目）**: 50って何？
- 50kg？
- 50ポンド？
- 50個？

**問題（2つ目）**: 8って？
- 8時間連続？
- 1日8時間を繰り返し？

**良い例**:
```
✅ REQ-001: AGVは50kg までの荷物を運搬しなければならない
✅ REQ-002: AGVは8時間 連続稼働できなければならない
```

## 3. 「〜すること」と「〜であること」の使い分け

### 機能要求と非機能要求の違い

| 種類 | 説明 | 書き方 | 例 |
|------|------|--------|---|
| **機能要求** | システムが「する」こと | 「〜しなければならない」 | AGVは荷物を運搬しなければならない |
| **非機能要求** | システムの「性質」 | 「〜でなければならない」 | AGVの最高速度は時速3kmでなければならない |

### 機能要求の例

```
✅ REQ-001: AGVは荷物をピックアップしなければならない
✅ REQ-002: AGVは障害物を検知しなければならない
✅ REQ-003: AGVは運搬履歴を記録しなければならない
```

**特徴**: 動詞が入る（運ぶ、検知する、記録する）

### 非機能要求の例

```
✅ REQ-004: AGVの最高速度は時速3kmでなければならない
✅ REQ-005: AGVの連続稼働時間は8時間でなければならない
✅ REQ-006: AGVの重量は200kg以下でなければならない
```

**特徴**: 状態を表す（速度、時間、重量）

## 4. ダメな要求の典型例と添削

### ダメ例1: 「使いやすいこと」

**悪い要求**:
```
❌ REQ-001: AGVは使いやすくなければならない
```

**添削プロセス**:

```
ステップ1: 「使いやすい」とは何か分解する
  → ボタンが少ない？
  → 操作が簡単？
  → マニュアル不要？

ステップ2: お客さんに確認
  「使いやすいって、具体的にどういう意味ですか？」
  お客さん: 「ボタン押すだけで動いてほしい」

ステップ3: 数値化・条件化
  → ボタン何個？
  → 何ステップで完了？

ステップ4: 良い要求に書き直す
```

**添削後**:
```
✅ REQ-001: AGVの運搬開始操作は、タッチパネルで3ステップ以内に完了しなければならない
✅ REQ-002: AGVの操作にマニュアル参照を必要としてはならない
```

### ダメ例2: 「高速に動作すること」

**悪い要求**:
```
❌ REQ-002: AGVは高速に動作しなければならない
```

**添削プロセス**:

```
ステップ1: 「高速」の意味を確認
  → 移動速度？
  → 応答時間？
  → 処理速度？

ステップ2: お客さんに確認
  「どれくらいの速さが必要ですか？」
  お客さん: 「指示してから、すぐ動いてほしい」

ステップ3: 「すぐ」を数値化
  → 1秒？ 5秒？ 10秒？
  お客さん: 「5秒くらいかな」
```

**添削後**:
```
✅ REQ-002: AGVは運搬指示受信後、5秒以内に移動を開始しなければならない
```

### ダメ例3: 「安全であること」

**悪い要求**:
```
❌ REQ-003: AGVは安全でなければならない
```

**添削プロセス**:

```
ステップ1: 「安全」の意味を分解
  → 人にぶつからない？
  → 荷物を落とさない？
  → 故障しない？

ステップ2: 全て列挙する

ステップ3: 検証方法を考える
```

**添削後**:
```
✅ REQ-003: AGVは前方15m以内の障害物（高さ30cm以上）を検知しなければならない
✅ REQ-004: AGVは障害物検知時、1m手前で停止しなければならない
✅ REQ-005: AGVは荷物の落下を検知した場合、即座に停止しなければならない
```

## 5. 実践演習: あなたの要求を添削してみよう

### 演習1: 次の要求を添削してください

**悪い要求**:
```
❌ REQ-001: システムは快適に動作しなければならない
```

**ヒント**:
- 「快適」とは何？
- 誰にとって快適？
- どうやって確認する？

**添削例**（クリックで表示）:
```
✅ REQ-001: システムは画面遷移を1秒以内に完了しなければならない
✅ REQ-002: システムは検索結果を3秒以内に表示しなければならない
```

### 演習2: 次の要求を添削してください

**悪い要求**:
```
❌ REQ-002: データは適切に保存されなければならない
```

**ヒント**:
- 「適切」とは何？
- どこに保存？
- いつ保存？
- 何件保存？

**添削例**:
```
✅ REQ-002: システムは運搬履歴を1000件までローカルストレージに保存しなければならない
✅ REQ-003: システムは運搬完了時に、履歴を自動的に保存しなければならない
```

### 演習3: 次の要求を添削してください

**悪い要求**:
```
❌ REQ-003: AGVは障害物を回避したり、荷物を運搬したり、充電したりしなければならない
```

**ヒント**:
- 1要求1条件
- 「または」「〜たり」は分割

**添削例**:
```
✅ REQ-003: AGVは前方の障害物を検知して回避しなければならない
✅ REQ-004: AGVは50kgまでの荷物を運搬しなければならない
✅ REQ-005: AGVはバッテリー残量20%以下で自動的に充電ステーションに移動しなければならない
```

## 6. 実践ポイント: 要求レビューチェックリスト（基礎編）

### 自分で書いた要求をチェック（8項目）

```
□ 抽象的な形容詞（使いやすい、高速、安全）を使っていないか？
□ 「適切に」「十分に」「必要に応じて」を使っていないか？
□ 「など」「等」を使っていないか？
□ 主語は明確か？（誰が／何が〜するのか）
□ 否定形ではなく肯定形で書いているか？
□ 1つの要求に複数の条件を詰め込んでいないか？
□ 「または」を使っていないか？
□ 単位を書いているか？（kg、秒、m、件など）
```

### 他人の要求をレビュー（3つの質問）

```
質問1: この要求を読んで、誰が読んでも同じ意味に解釈できますか？
質問2: この要求を、どうやってテストで確認しますか？
質問3: この要求は、技術的に実現可能ですか？
```

## 7. まとめ: 良い要求は「数値」と「条件」で決まる

**この記事のポイント**:

1. **良い要求の3条件**
   - 明確性: 誰が読んでも同じ意味
   - 検証可能性: テストで確認できる
   - 実現可能性: 技術的に可能

2. **8つの原則**
   - 抽象的な形容詞を使わない
   - 「適切に」「十分に」を使わない
   - 「など」を使わない
   - 主語を明確にする
   - 肯定形で書く
   - 1要求1条件
   - 「または」を使わない
   - 単位を必ず書く

3. **曖昧な言葉は数値化**
   - 「高速」→「100ms以内」
   - 「大量」→「1000件まで」
   - 「安全」→「検知率99%以上」

4. **ダメな要求は添削できる**
   - 「使いやすい」→ 分解 → 数値化 → 良い要求

**次回予告**:

第5回では、「良い要求の書き方【実践編】」を解説します。

- 検証可能性の深掘り（TAID）
- 要求ID採番ルール
- トレーサビリティマトリクスの作り方

第4回の基礎を踏まえて、実務で使える技術を学びます。
